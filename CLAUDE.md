# Job Search — Emerging Tech / AI Policy Analyst

Independent track, originally split out of the `side-hustle-job` worktree in another repo (G2AI_ME); has lived here standalone since 2026-07-24. Unrelated to G2AI in content — but the curator's background (AI governance for small states, international regulation) is directly relevant to the roles targeted.

**Principle: don't grow functionality just because we can.** A personal tool for one specific task, not a product or an enterprise system. Any development proposal (mine or the curator's) gets checked against real necessity, not "would be neat/polished" — see `docs/backlog/BACKLOG.md`, "Development recommendations" section, where this is applied in practice.

## What and why

Targeting an **Emerging Tech / AI Policy Analyst** position (analyst → director range, PM optional) at think tanks and international-org research units focused on policy/governance/global security/strategic stability around emerging tech and AI (NOT technical standardization).

Geo priority: **Tier A** (remote / Montenegro-Serbia) > **Tier B** (Western Europe) > **Tier C** (US/Japan, strong matches only). Out of scope: China, Russia, Middle East, Eastern Europe.

Curator's citizenship — Russian, ~4 years emigrated with no plans to return (stated openly in applications) — adds an extra filter specifically for Tier C (details and methodology in `docs/backlog/BACKLOG.md`).

Employment: full-time preferred, part-time also fine. Languages: fluent English and Russian, no others needed.

## Where things live

- **`docs/backlog/BACKLOG.md`** — status by tier, filtering methodology, plan, decision history and rejected options. Read here for detail, not this file.
- **`docs/ats-aggregator-sweep/notes.md`** — track 1: ATS-platform sweep (Lever/Greenhouse/Personio) for shortlist orgs.
- **`docs/job-aggregator-landscape/notes.md`** — knowledge update on query-centric job aggregators (JobSpy, RemoteOK, Himalayas, Adzuna) — shift from org-centric to query-centric approach.
- **`docs/tech_specs/query-connectors/spec.md`** — spec for query-centric connectors (Himalayas/Adzuna/JobSpy), a second family complementing org-centric ATS. Status: implemented.
- **`docs/tech_specs/triage-and-autonomy/spec.md`** — spec for LLM relevance triage, run reliability, and unattended scheduling. Status: run reliability + scheduling (systemd timer, 00:00 UTC) implemented 2026-07-26; LLM relevance triage remains a draft.
- **`docs/tech_specs/postings-schema-hardening/spec.md`** — spec for `postings` schema robustness: two-layer input validation (connector boundary + `store.py` backstop against `sqlite3.IntegrityError`), STRICT + `CHECK(status)` migration, cross-source `dedup_key` symmetry between the ATS and search storage families. Status: implemented 2026-08-04.
- **`docs/tech_specs/vercel-web-gui/spec.md`** — spec for a hosted card-view GUI on Vercel, replacing local Streamlit. Status: implemented and live at `https://ai-policy-jobs.vercel.app` (2026-08-04).
- **`docs/tech_specs/web-postgres-migration/spec.md`** — spec for migrating the web GUI's storage from SQLite-in-Vercel-Blob to Neon Postgres: real server-side filtering/pagination, `organizations`/`searches` tables synced from the YAML configs, Alembic migrations, full-text search. Status: implemented 2026-08-04.
- **`.claude/commands/`** — custom commands, working as pairs: **`/tech-spec`** turns a request into a spec following the `docs/tech_specs/<slug>/spec.md` convention (commit plan, checklist, open questions, out of scope) and commits nothing; **`/feature-workflow`** is its direct continuation — picks up a spec at `черновик v<N>`, resolves open questions first, then executes the commit plan commit by commit and finally flips status to `реализовано (<sha>..<sha>)`.
- **`config/orgs.yaml`** (org-centric: known org → ATS) + **`config/searches.yaml`** (query-centric: search term → orgs/postings from the data) + **`scripts/`** — the job-monitoring tool → local SQLite (`data/jobs.db`, gitignored). `scripts/run.py` (orchestrator) and `scripts/store.py` (persistence) stay at the top level — `run.py` is the systemd `ExecStart` target (`docs/user_guides/cli_reference.md`), moving it would touch a live unit outside git. The six source connectors live under `scripts/connectors/{ats,query}/`, split along the same ATS/query-centric line as `config/`. Run: **`.venv/bin/python scripts/run.py`** (NOT bare `python3` — system Python lacks `python-jobspy`/`pandas`). Since 2026-07-25 one run covers every source including LinkedIn; the `--linkedin` flag stays in the code but no spec is marked `manual: true` anymore, so it's currently a no-op. `run.py.__main__` also drives `scripts/postgres_sync.py`, mirroring `store.py`'s result into Neon Postgres for the web GUI (`docs/tech_specs/web-postgres-migration/spec.md`) — `store.py`'s own upsert/reconciliation logic is untouched by this, it's a downstream mirror, not a second write path.
- **`app/app.py`** + **`.streamlit/config.toml`** — local card-view UI for browsing postings (Streamlit, shares the repo's single `.venv/`), deliberately kept separate from `scripts/` (ingestion) — same split `web/` follows. Curator kept it running alongside `web/` as of 2026-08-04, pending acceptance of the new GUI; retiring it is a separate future commit. Run: `.venv/bin/streamlit run app/app.py`.
- **`web/`** — hosted card-view GUI on Vercel (`docs/tech_specs/vercel-web-gui/spec.md`, storage migrated to Postgres by `docs/tech_specs/web-postgres-migration/spec.md`), live at `https://ai-policy-jobs.vercel.app`, gated by a `SITE_PASSWORD` cookie. `web/api/` — Python Vercel Functions (`postings.py`/`status.py`/`facets.py`/`login.py`, thin wrappers around `_repo.py`); self-contained, does NOT import `scripts/store.py` (a deployed Function can't reach outside its Vercel Root Directory). `web/api/_schema.py` — shared SQLAlchemy Core schema (`postings`/`organizations`/`searches`), portable across SQLite (tests) and Postgres (prod) except `search_vector` (Postgres-only full-text search column, added by a raw-SQL Alembic migration, no SQLite equivalent). `web/api/_repo.py` — the single source of truth for filtering/pagination, queries Neon directly (`DATABASE_URL`); `facets.py` exposes a dedicated `SELECT DISTINCT` query for the tier/org filter widgets, deliberately not a large `/api/postings` page (that has an inherent row-count ceiling that silently drops orgs past it — live-caught 2026-08-04). `web/public/` — vanilla HTML/CSS/JS, no build step, thin client (server-side pagination, "Load more"). `alembic/` (repo root) — migrations for the Postgres schema, `env.py` imports `web/api/_schema.py`'s metadata across that same local-only boundary. `scripts/postgres_sync.py` mirrors `data/jobs.db` into Postgres from `run.py`'s `__main__` (replaces the earlier Blob-sync approach — see below). Deploy: `cd web && vercel deploy --prod` (project already linked).
- **`tests/`** — pytest, hermetic by default (never touches live `data/jobs.db`, never opens a real network connection or real Postgres), mirrors `scripts/`'s layout (`tests/connectors/{ats,query}/`). A separate `integration` marker (`tests/integration/`) covers what genuinely needs real Postgres (Alembic migrations, full-text search ranking) — excluded from the default run (`pyproject.toml`'s `addopts`), exercised only by CI's `test-integration` job against a `postgres:17` service container. Run: `.venv/bin/pytest` (default tier); `.venv/bin/pytest -m integration` with `DATABASE_URL` set for the other.
- **Tooling** — `ruff`/`mypy` (config in `pyproject.toml`, deps in `requirements-dev.txt`) cover `scripts/`+`app/`+`web/`+`alembic/` (the last exempted from `E501`/`I001` — autogenerated, not hand-reformatted); `eslint` (flat config `eslint.config.js`, deps in `package.json`) covers `web/public/**/*.js`. `uv` (already on the machine) is the local venv/install tool — see `docs/user_guides/cli_reference.md`, "Окружение". `requirements.txt`/`requirements-dev.txt` stay the dependency source of truth (both CI and Dependabot's `pip` ecosystem read them); `uv` installs from them, it doesn't replace them. `web/requirements.txt` is separate — it's what Vercel's Python build actually installs for the deployed functions (`sqlalchemy`+`psycopg[binary]`), not read by CI/Dependabot; `alembic` itself is scripts-only (migrations run locally, never inside the deployed function) and lives only in the root `requirements.txt`.
- **`docs/user_guides/cli_reference.md`** — short command cheat sheet for manual operation (venv/tooling bootstrap, Streamlit UI address, direct DB access, config format).
- **`.github/`** — CI (`workflows/tests.yml`: a `test` job running `ruff check` + the default `tests/` tier, and a `test-integration` job running the `integration`-marked tests against a `postgres:17` service container) + `dependabot.yml` (pip + npm + github-actions, weekly). No branch protection — GitHub Pro is required for that on a private personal-account repo.
