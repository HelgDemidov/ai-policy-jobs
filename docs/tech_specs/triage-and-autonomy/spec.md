# Спек: триаж релевантности и автономный прогон

Статус: **частично реализовано** (`§3` надёжность + `§4` планировщик, 2026-07-26) · LLM-триаж релевантности (`§1`, `§2`, `§5`) — вне скоупа этого захода, остаётся черновиком
Происхождение: `docs/backlog/BACKLOG.md` → «Рекомендации по развитию (2026-07-25)», переработано после разбора на живых данных

## 0. Что и зачем

В базе 200 вакансий, и **все до одной в статусе `new`** — размечена ноль. Из шортлиста (`orgs.yaml`) пришла 31 строка, остальные 169 — из query-centric поиска, где заметная часть мимо темы. Инструмент научился собирать, но не помогает выбирать: 200 карточек за один заход не разбираются, а размечать их вручную, чтобы потом фильтровать по разметке, — та же работа в профиль.

Цель: дать карточкам порядок (ранжирование вместо ручного перебора) и только после этого — держать базу свежей без участия куратора.

Граница скоупа: новых источников не добавляем, семантику двух семей хранения не трогаем.

## 1. Триаж релевантности — `scripts/triage.py`

- Колонки `relevance INTEGER` (0–100) и `relevance_note TEXT`; миграция по образцу `_ensure_dedup_key_column` (`store.py:55`) — идемпотентный `ALTER TABLE` при отсутствии колонки, `DROP` недопустим (живая БД).
- **Отдельный скрипт, не внутри `run.py`.** Сбор не должен зависеть от доступности и стоимости внешнего платного API.
- Один запрос на вакансию, модель `claude-opus-5`, structured output через `client.messages.parse()` с Pydantic-схемой `{relevance: int, tier_verdict: str, note: str}`.
- Критерии берутся из уже написанного `docs/backlog/BACKLOG.md`: тиры A/B/C, полностью исключённые гео (Китай, Россия, Ближний Восток, Восточная Европа), методология Tier C по гражданству (clearance-gated / sponsorship-gated / mission-adversarial), «НЕ техническая стандартизация». Блок между запросами не меняется → `cache_control: {"type": "ephemeral", "ttl": "1h"}`. TTL именно часовой: 200 последовательных запросов не уложатся в пятиминутный по умолчанию. Минимум кэшируемого префикса на Opus 5 — 512 токенов, блок критериев заведомо крупнее.
- Идемпотентность: обрабатываются только строки `WHERE relevance IS NULL`; повторный прогон — no-op, как и повторный `run.py`.
- Изоляция сбоя: ошибка на одной вакансии оставляет строку `NULL` и не роняет цикл — тот же паттерн, что `run.py:43`.
- Ключ `ANTHROPIC_API_KEY` — из `.env`. Разбор KEY=VALUE уже написан в `adzuna.py:21`, но зашит под имена Adzuna: вынести парс в `query_common.load_env() -> dict`, оба вызывающих переиспользуют. Это дедупликация существующего кода, а не новый механизм.
- **Замеренная стоимость** (по фактической БД, не по оценке): 791 905 символов ≈ 220K токенов на все описания целиком; 191 903 ≈ 53K токенов на `title + org + location + первые 1200 символов описания` — для решения достаточно второго. При $5/$25 за MTok с кэшированием критериев — **≈$0.40–0.80 за разовый прогон всей базы**, ежедневный инкремент в 10–30 вакансий — центы. Стоимость не является фактором при выборе модели на этом объёме.
- Известное ограничение: у строк `jobspy_linkedin` описания пустые (15 из 15, `AVG(LENGTH(description)) = 0` — следствие `linkedin_fetch_description=False`). Судить придётся по `title + org + location`; на первичный отсев хватает, потому что решает организация.

## 2. Запросы в `searches.yaml`: добавить узкие, широкие оставить

**Посылка первоначальной рекомендации не подтвердилась и здесь исправлена.** Живой зонд Himalayas (2026-07-25, публичный `/jobs/api/search`, 3 страницы):

| запрос | результатов | явный шум в титуле |
|---|---:|---:|
| `policy` | 40 | 3 (7,5%) |
| `AI governance` | 45 | 7 (16%) |
| `technology policy` | 14 | 0 |
| `tech policy` | 7 | 0 |

Утверждение «`policy` — главный генератор шума» **неверно**: доля мусора у `AI governance` вдвое хуже. Узкие фразы дают почти чистую выдачу, но обрушивают охват вчетверо. Поэтому замена широких запросов узкими **отвергается**: она купила бы точность ценой полноты у инструмента, чья задача — не пропустить вакансию.

Правка: **добавить** `technology policy` и `tech policy` отдельными спеками, `policy` и `AI governance` сохранить как широкую сеть. За точность отвечает §1, а не сужение запросов. Цена: +2 спека × до 3 страниц (`himalayas.py:16`, `PAGES = 3`) = +6 HTTP-запросов на прогон. Текущий прогон — ≈15–20 запросов (Himalayas тянет по 3 страницы на спек; в раннем обсуждении фигурировала цифра 10 — она считала спеки, а не запросы).

## 3. Надёжность `run.py` — до автоматизации, не после

1. **Ненулевой exit code.** Сейчас `main()` завершается нулём всегда, включая прогон, где упали все источники. Под планировщиком «всё сломалось» становится неотличимо от «нового нет», и `systemctl --user list-timers` показывает зелёный успех. Считать успешные источники, `sys.exit(1)` при нуле успешных.
2. **Защита от пустого ответа ATS.** `upsert_postings` при пустом списке помечает все `new`-строки организации `likely_closed` (`store.py:121–125`). Успешный HTTP-ответ с пустым массивом (переименовали slug, сменился формат) неотличим от «организация закрыла все вакансии» — под ежедневным таймером это шанс на тихую массовую архивацию раз в сутки. Правка: если список пуст, а у пары `org+source` в базе есть строки — реконсиляцию пропустить, напечатать предупреждение.

## 4. systemd user timer

**Реализовано 2026-07-26** — расписание разошлось с исходным планом ниже по прямому решению куратора: не `11:00` локального времени, а **`00:00` по Гринвичу** (`OnCalendar=*-*-* 00:00:00 UTC`, суффикс `UTC` обязателен — локальный часовой пояс машины Europe/Podgorica). Полночь как таковая исходно была отвергнута именно из-за риска простаивающей машины — риск принят осознанно, компенсируется тем же `Persistent=true`, что уже был в плане. `RandomizedDelaySec=30m` из исходного плана опущен: точность момента (ровно полночь) поставлена выше вежливости к API при глобальном стечении таймеров. `ExecStart` один — `run.py`; второй (`triage.py`) добавится, когда/если LLM-триаж (`§1`) будет реализован отдельным заходом.

Два юнита живут в `~/.config/systemd/user/` этой машины, в репозиторий не кладём (абсолютные пути), полный текст и разбор `WorkingDirectory`/`ExecStart` кавычек — в `docs/user_guides/cli_reference.md`. `Type=oneshot`. Путь содержит пробел и кириллицу, поэтому `ExecStart` обязан быть в кавычках — проверено `systemd-analyze --user verify` на systemd 255 (там же живьём поймана обратная ошибка: `WorkingDirectory` в кавычках не работает — это не командная строка). `loginctl enable-linger` **не нужен**: при ежедневном входе в сессию `Persistent=true` догоняет пропуск сам. Логи — `journalctl --user -u`; отдельный лог-файл и ротацию не заводить.

Живьём проверено: `systemd-analyze --user verify` зелёный, ручной `systemctl --user start job-search-run.service` отработал и залогировался в journald, `enable --now` на таймере показал корректный следующий запуск (`02:00 CEST` = `00:00 UTC` летом). Не проверялось живьём: реальный догон пропущенного полуночного окна (`Persistent=true`) — потребовал бы держать машину выключенной через полночь; логика самого флага стандартна для systemd, отдельно не тестировалась.

Исходное расписание `11:00` из плана ниже сохранено как история решения, не как альтернатива на будущее.

## 5. UI: `app.py`

Сортировка `ORDER BY relevance DESC NULLS LAST` вместо текущей по дате (`app.py:69`); чип с оценкой на карточке; возраст `last_seen` на карточке — это закрывает дыру, при которой вакансия, размеченная `reviewed` и потом закрытая, визуально неотличима от живой (реконсиляция ручные статусы не трогает — `store.py:118`, и правильно делает).

## Design rationale / отвергнутые альтернативы

- **Сузить широкие запросы вместо добавления узких** — отвергнуто замером (§2): точность растёт, полнота падает вчетверо.
- **Табы по статусу как первый шаг UI** (исходная рекомендация бэклога) — отвергнуто замером: все 200 строк `new`, ось имеет одно значение; получилась бы одна вкладка с 200 карточками и три пустые. Вернуться, когда разметка появится.
- **Группировка по tier** — отвергнуто: тир почти коллинеарен источнику (himalayas→A 82/82, adzuna→B 55/55), о качестве не сообщает ничего.
- **Отдельный org-blocklist** для мусорных работодателей — отвергнуто: §1 его поглощает, третий механизм для той же задачи.
- **Batch API** (−50% стоимости) — отвергнуто: polling и задержка до 24 часов ради экономии ≈$0.30.
- **Отдельная таблица/хранилище архива** — отвергнуто: `likely_closed` уже soft-delete, на 200 строках отдельное хранилище оверинжиниринг.
- **Встроить триаж в `run.py`** — отвергнуто: связало бы сбор с доступностью платного внешнего API.
- **`cron` вместо systemd-таймера** — отвергнуто: не догоняет пропущенный запуск на выключенной машине, что для десктопа означает «не работает никогда».
- **Airflow / Prefect** — оверкилл для одной команды раз в сутки.

## Тестовое покрытие

Герметичность обязательна: боевая `data/jobs.db` не затрагивается, сеть в тестах недопустима. Структурной защиты при этом **нет** — в `tests/conftest.py` только фикстура сброса Streamlit-кэша; чистота держится на том, что каждый тест явно передаёт `tmp_path` и переопределяет `searches_path`. Проверять замером числа строк до/после прогона (`/feature-workflow`, шаг 5). Coverage-гейта в репозитории нет; критерий — зелёный `.venv/bin/pytest` и покрытие каждой новой ветки.

- **Коммит 1** (store + надёжность) — **выполнено 2026-07-26**, кроме миграции `relevance`/`relevance_note` (часть LLM-триажа, не в этом заходе): пустой ответ ATS при непустой истории → реконсиляции нет, предупреждение есть (`test_empty_response_with_existing_history_skips_reconciliation`); пустой ответ при пустой истории → прежнее поведение, no-op (`test_empty_response_with_no_history_is_a_harmless_noop`); скоуп по org+source (`test_empty_response_guard_is_scoped_to_org_and_source`); `main()` с нулём успешных источников → exit 1 (`test_main_returns_1_when_every_attempted_source_fails`), с частичным/кросс-семейным отказом → exit 0 (`test_main_returns_0_when_a_source_in_either_family_succeeds`), с пустым конфигом → exit 0, не ошибка (`test_main_returns_0_when_config_is_completely_empty`).
- **Коммит 2** (triage): монкипатч клиента Anthropic — сетевых вызовов быть не должно; обрабатываются только `relevance IS NULL`; ошибка на одной строке не роняет цикл; повторный прогон даёт 0 обновлений; `query_common.load_env` — файл есть/нет, приоритет `os.environ`.
- **Коммит 3** (searches + app): `derive_tier` для новых спеков (himalayas→A); `AppTest` — сортировка по `relevance`, карточка с `NULL` не падает.

## Открытые вопросы

- Порог `relevance`, ниже которого карточка скрывается по умолчанию (40? 50?). Решается после первого живого прогона по фактическому распределению оценок, а не заранее.
- Нужен ли флаг переоценки уже размеченных строк после правки критериев. Не закладываю до первого реального случая.

## Вне скоупа

- Черновики откликов — LLM выдаёт только оценку и пояснение.
- Уведомления (Telegram/email): канала наружу нет, база обновляется молча — отдельное решение куратора.
- HTML-скрейп карьерных страниц (п.2 «Следующих шагов» бэклога).
- `fetch_description: true` для LinkedIn — запрос на каждую вакансию, ≈×20 за прогон.
- Правка тира из карточки Streamlit; сворачивание org-мультиселекта.
