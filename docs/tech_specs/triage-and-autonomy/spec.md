# Спек: LLM-триаж релевантности вакансий

Статус: черновик v1 · 2026-08-05
Происхождение: `docs/backlog/BACKLOG.md` → «Актуальное / открытые задачи» п.1; пересборка с нуля прежнего черновика (2026-07-25), который смешивал уже сделанное (надёжность `run.py` + systemd-таймер, оба реализованы 2026-07-26 — теперь только в `BACKLOG.md`/`docs/user_guides/cli_reference.md`) с так и не реализованным триажем — куратор попросил развести по разным документам.

## 0. Что и зачем

Живой замер (`data/jobs.db`, 2026-08-05): 351 строка, 350 в статусе `new` — размечена одна. Инструмент научился собирать, но не помогает выбирать: карточки за один заход не разбираются, размечать вручную ради последующей фильтрации — та же работа в профиль. Цель: дать карточкам порядок (ранжирование вместо перебора), без нового источника данных и без изменения семантики двух семей хранения.

Граница скоупа: оценка релевантности + её отражение в веб-GUI. Сбор данных и хранение не трогаются.

## 1. `scripts/triage.py` — LLM-оценка релевантности

- Колонки `relevance INTEGER` (0–100) и `relevance_note TEXT` — **на обоих хранилищах**, не только SQLite: `store.py` (миграция по образцу `_ensure_dedup_key_column`, `store.py:90`, идемпотентный `ALTER TABLE`) И `web/api/_schema.py`'s `postings`-таблица + новая Alembic-миграция `0004_add_relevance.py`. Прежний черновик этого не учитывал — написан до Postgres-миграции веб-GUI. `scripts/postgres_sync.py`'s `_POSTINGS_COLUMNS` (жёстко перечисленный список, не `SELECT *`, см. `postgres_sync.py:41`) тоже требует добавления обеих колонок — иначе оценка запишется локально и никогда не долетит до прод-БД, откуда её читает веб-GUI.
- Отдельный скрипт, не внутри `run.py` — сбор не должен зависеть от доступности/стоимости платного внешнего API.
- Один запрос на вакансию, `claude-opus-5`, `client.messages.parse()` + Pydantic-схема `{relevance: int, tier_verdict: str, note: str}`.
- Критерии — из `docs/backlog/BACKLOG.md` («Вводные о кураторе» + «Методология фильтрации Tier C»); неизменный между запросами блок → `cache_control: {"type": "ephemeral", "ttl": "1h"}` (часовой TTL: 350+ последовательных запросов не уложатся в пятиминутный дефолт; блок критериев крупнее минимального кэшируемого префикса Opus 5, 512 токенов).
- Идемпотентность: обрабатываются только строки `WHERE relevance IS NULL`; повторный прогон — no-op.
- Изоляция сбоя: ошибка на одной вакансии оставляет `NULL`, не роняет цикл (тот же паттерн, что per-source изоляция в `run.py`).
- `ANTHROPIC_API_KEY` из `.env` через новый `query_common.load_env() -> dict` — обобщение уже существующего `adzuna.py:_load_env_credentials` (сейчас зашито под имена Adzuna полей), не новый механизм, дедупликация существующего кода.
- **Стоимость, свежий замер (2026-08-05; было 200 строк/2026-07-25, теперь 351):** truncated-подход (`title+org+location`+первые 1200 символов описания) — 335K символов ≈ 93K токенов на полный прогон всей базы. `claude-opus-5`: $5/$25 за MTok (живьём подтверждено, август 2026) — с кэшированием критериев ≈$0.70–1.40 за разовый прогон всей текущей базы; ежедневный инкремент (10–30 новых вакансий) — единицы центов. Не фактор при выборе модели на этом объёме.
- Известное ограничение: у строк `jobspy_linkedin` описания пустые (`linkedin_fetch_description=False`) — судить по `title+org+location`; для первичного отсева достаточно, потому что решает организация.

## 2. `config/searches.yaml` — узкие запросы в дополнение к широким

Ещё не сделано (проверено живьём — в текущем `searches.yaml` только `policy`/`AI governance`). Живой зонд Himalayas (2026-07-25, `/jobs/api/search`, 3 страницы): `policy` — 40 результатов/7,5% явного шума в титуле; `AI governance` — 45/16%; `technology policy` — 14/0%; `tech policy` — 7/0%. Узкие фразы почти чистые, но обрушивают охват вчетверо — замена широких запросов узкими отвергнута (Design rationale), точность вместо этого обеспечивает §1.

Добавить `technology policy` и `tech policy` отдельными спеками, `policy`/`AI governance` сохранить как широкую сеть. Цена: +2 спека × до 3 страниц (`himalayas.py`, `PAGES = 3`) = +6 HTTP-запросов на прогон (текущий прогон — ≈15–20 запросов).

## 3. Веб-GUI — ранжирование по релевантности

`web/api/_repo.py`'s `_build_where` — сейчас порядок по умолчанию `COALESCE(posted_at, first_seen) DESC` (`_repo.py:68`). Когда `relevance` не `NULL` — сортировать по нему, вторичный ключ та же дата-эвристика, чтобы размеченные и ещё не размеченные строки не перемешивались хаотично: `ORDER BY relevance DESC NULLS LAST, COALESCE(posted_at, first_seen) DESC`. Не путать с уже существующей `ts_rank`-сортировкой полнотекстового поиска (`_repo.py:79`) — та включается только при непустом `query`, независимая ветка, конфликта нет.

`web/public/app.js`/`index.html` — чип с оценкой на карточке (по образцу tier-чипа). `web/api/postings.py` уже отдаёт все колонки `postings` как есть — новых полей в API добавлять не нужно.

## Design rationale / отвергнутые альтернативы

- **Сузить широкие запросы вместо добавления узких** (§2) — отвергнуто замером: точность растёт, полнота падает вчетверо.
- **Табы по статусу как первый шаг UI** — отвергнуто замером на живых данных: подавляющее большинство строк в статусе `new`, ось имеет практически одно значение — получилась бы одна переполненная вкладка и пустые остальные. Вернуться, когда разметка появится.
- **Группировка по tier** — отвергнуто: тир почти коллинеарен источнику (himalayas→A, adzuna→B), о качестве конкретной вакансии не сообщает ничего.
- **Отдельный org-blocklist** для мусорных работодателей — отвергнуто: §1 его поглощает, не заводить третий механизм для той же задачи.
- **Batch API** Anthropic (−50% стоимости) — отвергнуто: polling и задержка до 24 часов ради экономии на объёме, где абсолютная сумма и так копеечная.
- **Встроить триаж в `run.py`** — отвергнуто: связало бы ежедневный сбор данных с доступностью и стоимостью платного внешнего API.

## Открытые вопросы

- Порог `relevance`, ниже которого карточка скрывается по умолчанию (40? 50?) — решается после первого живого прогона по фактическому распределению оценок, не заранее.
- Нужен ли флаг переоценки уже размеченных строк после правки критериев — не закладывается до первого реального случая.

## Вне скоупа

- Автоматический запуск `triage.py` по расписанию (второй `ExecStart` в systemd-таймере) — сначала ручной прогон, автоматизация решается отдельно после проверки порога/стоимости на практике.
- Черновики откликов — LLM выдаёт только оценку и пояснение.
- Уведомления (Telegram/email) — канала наружу нет, база обновляется молча, отдельное решение куратора.
- HTML-скрейп карьерных страниц без ATS — отдельный пункт `BACKLOG.md`, не этот спек.
- `fetch_description: true` для LinkedIn — запрос на каждую вакансию, ≈×20 за прогон.
