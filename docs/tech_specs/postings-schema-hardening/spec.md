# Спек: устойчивость схемы `postings` (краш org=NULL + оздоровление)

Статус: черновик v1 · 2026-08-04
Происхождение: прямой запрос куратора — живой краш `job-search-run.service` (2026-08-04, `sqlite3.IntegrityError: NOT NULL constraint failed: postings.org`), затем `/brainstorming` по системным рискам схемы

## 0. Что и зачем

Ночной прогон `run.py` падает и теряет остаток батча (`jobspy_linkedin`, `jobspy_indeed`, `expire_stale_search_postings` в ту ночь не выполнились), когда query-centric коннектор отдаёт запись без `org`. Разбор по `/brainstorming` (живые проверки, не гипотезы — см. каждый пункт ниже) вскрыл этот краш как частный случай более общего пробела: недоверенные внешние данные долетают до `NOT NULL`-констрейнтов без валидации, и заодно нашёл асимметрию в дедупе между двумя семьями хранения. Все четыре части ниже — один согласованный дизайн, не отдельные фиксы.

Граница скоупа: схема и запись в неё. Сами коннекторы (что и как парсят) и сбор данных не трогаются, кроме точки отсева невалидных записей.

## 1. Корневая причина

`adzuna.py:65` — `"org": (r.get("company") or {}).get("display_name")`. Живой запрос к Adzuna (`what_phrase=think tank`, gb, 50 результатов) — 2 записи без `company.display_name` (агентские/анонимизированные вакансии). `himalayas.py:41` (`j.get("companyName")`) и `jobspy_search.py:46` (`_clean(row.get("company"))`) — тот же класс риска, той же формы `.get()`-цепочка без отсева. `store.py:179` (`upsert_search_postings`) кладёт `p["org"]` в INSERT без проверки; `postings.org NOT NULL` останавливает вставку исключением. `run.py`'s `_run_search_connectors` оборачивает в try/except только `fetch(spec)` (строка 72), не последующий `store.upsert_search_postings` — исключение пробрасывается из `main()` и убивает весь оставшийся цикл. ATS-семья структурно защищена по `org` (берётся из `orgs.yaml`, не из ответа API), но не по `title`/`url`/`ats_id` тем же классом риска в принципе.

## 2. Слой 1 — отсев на границе коннектора

В `adzuna.py`/`himalayas.py`/`jobspy_search.py` — пропуск записи перед добавлением в результат `fetch()`, если `org`/`title`/`url` пусты. Паттерн — с `app/infrastructure/scopus_client.py` (`if not doi: continue  # статьи без DOI не сохраняем — низкая ценность`) из соседнего, более зрелого проекта куратора: отсев там, где известна причина пропуска, с комментарием почему.

`jobspy_search.py` — отдельный нюанс: `ats_id = str(ats_id)` (строка 45) превращает Python `None` в строку `"None"` (truthy!) до того, как её можно проверить обычным `if not ats_id`. Фикс — `_row_to_posting` возвращает `None` при `ats_id is None` (до `str()`), `fetch_linkedin`/`fetch_indeed` фильтруют `None` из результата списком-включением — `[p for p in (...) if p is not None]`. `adzuna.py`/`himalayas.py` не подвержены: их `ats_id` берётся из обязательного ключа ответа (`r["id"]`/`j["guid"]`) — отсутствие дало бы `KeyError`, не `None`.

## 3. Слой 2 — бэкстоп в `store.py`

В обеих `upsert_postings` и `upsert_search_postings` — INSERT и UPDATE оборачиваются в `try/except sqlite3.IntegrityError`: лог (`print`, стиль уже есть для empty-response guard, `store.py:135`) + пропуск записи + `continue` батча, вместо падения всей функции. Не дублирует слой 1 — слой 1 ловит конкретно три известных поля по бизнес-смыслу («вакансия без работодателя нетриажируема»), слой 2 ловит вообще любое нарушение DB-констрейнта, включая те, что мы сейчас не предвидим (в т.ч. будущий `CHECK` на `status`, п.4).

## 4. Миграция на STRICT + `CHECK(status)`

Пересоздание `postings` в `STRICT`-таблицу с `CHECK(status IN ('new','reviewed','applied','rejected','likely_closed'))` (список — as-is `STATUS_OPTIONS` из `app/app.py:18`). `tier` остаётся обычным `TEXT` без CHECK — уже поддерживает составные значения («A/B», `app/app.py:19`), это осознанный неэнам, не пробел.

Живьём проверено (не гипотеза):
- `SELECT strict FROM pragma_table_list('postings')` — рабочий идемпотентность-чек (0/1).
- Явная Python-транзакция (`CREATE TABLE ... STRICT` → `INSERT ... SELECT` → `DROP` → `RENAME` → `COMMIT`) при исключении посреди последовательности откатывается целиком — симуляция краха оставила исходную таблицу и данные нетронутыми.
- STRICT для `TEXT`-колонки НЕ отвергает число — конвертирует в текст (`123` → `'123'`), отвергает только `BLOB`. Для `INTEGER`-колонки (будущий `relevance` из triage-and-autonomy) STRICT реально отвергает нечисловую строку. **Для самого бага из §1 STRICT не добавляет ничего сверх уже существующего `NOT NULL`** — его польза здесь чисто в самодокументировании схемы плюс защита будущего `relevance INTEGER`. Куратор одобрил включение осознанно, «без иллюзий о добавленной стоимости» — не продавать как решение бага.
- `ALTER TABLE ADD COLUMN` на STRICT-таблице работает нормально — расширяемость (`relevance`/`relevance_note`) не ломается переходом.

Процедура — новая функция в `store.py`, вызывается безусловно (идемпотентно) из `open_db()`: чек strict-флага → если 0, файловый бэкап `data/jobs.db` → транзакция с явным списком колонок и сверкой `COUNT(*)` до/после перед `DROP` → любое исключение пробрасывается дальше (громкий отказ лучше тихой рассинхронизации; событие одноразовое — 323 строки/1.7 МБ сейчас, миграция дешёвая). `SCHEMA`-константа (историческая, non-strict) не меняется — как и с `dedup_key`, миграция сама доводит любую БД (новую или старую) до актуального состояния.

## 5. Симметрия `dedup_key` между семьями хранения

`upsert_search_postings` (`store.py:174`) проверяет `dedup_key` против **всех** источников перед вставкой — кросс-source дедуп работает. `upsert_postings` вычисляет и сохраняет `dedup_key` (строка 101), но никогда не проверяет его перед INSERT — только `(source, ats_id)`. Живой запрос к боевой БД: 0 текущих коллизий (асимметрия пока не проявилась видимо, структурный пробел подтверждён чтением кода, не наблюдением сбоя).

Фикс: в `upsert_postings`, в ветке `row is None`, перед INSERT — тот же поиск по `dedup_key`, что уже есть в `upsert_search_postings`. Совпадение найдено → `UPDATE ... SET last_seen=? WHERE id=?` на существующей строке, не вставлять новую, не переписывать её остальные поля (симметрия с уже существующим поведением search-семьи, не новая функциональность). Реконсиляцию не затрагивает: `ats_id` добавляется в `seen_ids` безусловно до дедуп-проверки, а реконсиляция скопирована по `org+source` — к чужой (другого source) строке не обращается.

## Design rationale / отвергнутые альтернативы

- **Relax `NOT NULL` на `org`** — отвергнуто: `org` — стержень всей модели тира/фильтрации, вакансия без работодателя нетриажируема по методологии `docs/BACKLOG.md`.
- **Плейсхолдер типа `"Unknown"` вместо org** — отвергнуто: засоряет org-мультиселект в UI и дедуп-ключ мусорными совпадениями.
- **Только слой коннектора ИЛИ только слой store, не оба** — отвергнуто: разные классы защиты (бизнес-смысл на границе источника vs структурная гарантия на записи), взаимно не заменяют друг друга.
- **Отдельный фикс коллизии `dedup_key` при `org=None`** (`f"{None} {title}"` → `"none <title>"` мог бы схлопнуть разных неизвестных работодателей) — не чинится отдельно, снимается сама как побочный эффект §2: записи без org до вставки не доходят вовсе.
- **«Апгрейд» существующей строки более авторитетными ATS-данными при дедуп-совпадении** (§5) — отвергнуто как отдельная гипотетическая фича поверх фикса асимметрии; текущий фикс — чистая симметрия с уже существующим поведением search-семьи.
- **Обобщение `_ensure_dedup_key_column` (`store.py:55`) → `_ensure_column(conn, name, ddl)`** — рассмотрено, отвергнуто: STRICT-миграция (§4) — пересоздание таблицы (`CREATE`→`INSERT`→`DROP`→`RENAME`), не `ALTER TABLE ADD COLUMN`, обобщённый хелпер ей не нужен структурно. Второй ADD-COLUMN случай, отмеченный в `triage-and-autonomy/spec.md` как повод обобщить, этим спеком не наступает — реальный кандидат появится вместе с колонками `relevance`/`relevance_note`, когда triage-спек будет реализовываться.
- **`CHECK` на `source` или `tier`** — отвергнуто: `source` полностью внутренний (константы в `run.py`, не внешние данные — опечатка там баг кода, а не runtime data-quality проблема, ловится тестами); `tier` осознанно поддерживает составные значения.
- **Fuzzy/семантический дедуп** — не в скоупе, уже отвергнуто в `query-connectors/spec.md` на этом масштабе, не пересматривается.

## Тестовое покрытие

Герметично — `tmp_path`, без сети, боевая `data/jobs.db` не трогается тестами. Живой прогон миграции на реальной БД — отдельно вручную, вне suite, с файловым бэкапом.

- **Коммит 1** (`store.py` бэкстоп): `upsert_search_postings`/`upsert_postings` с `org=None`/`title=None` в батче — не крашит, пропущенная запись не вставлена, остальные вставлены, `new_count` верный.
- **Коммит 2** (коннекторы): для каждого из adzuna/himalayas/jobspy_search — замоканный ответ с одной «плохой» записью вперемешку с валидными → плохая исключена, валидные проходят; существующие тесты не сломаны.
- **Коммит 3** (STRICT+CHECK): старая non-strict БД с данными → после миграции `strict=1`, CHECK на невалидный `status` отвергает, `COUNT(*)` сохранён, повторный запуск — no-op.
- **Коммит 4** (dedup-симметрия): `upsert_postings` с `dedup_key`, совпадающим с существующей строкой другого `source` → touch `last_seen`, новая строка не вставлена, реконсиляция остальных ATS-записей этого `org+source` не задета.
