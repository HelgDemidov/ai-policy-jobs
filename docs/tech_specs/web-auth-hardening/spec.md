# Спек: укрепление аутентификации и безопасности `web/`

Статус: реализовано (`d5b9138`..`be3f2ab`) · 2026-08-05
Происхождение: прямой запрос куратора — критический аудит (`/brainstorming` + `/systematic-debugging`, 2026-08-05) архитектурной чистоты и безопасности `web/` от фронтенда до БД, по итогам которого куратор попросил `/tech-spec`.

## 0. Что и зачем

Аудит нашёл пять пробелов в гейте `web/api/_auth.py` (spec `vercel-web-gui/spec.md` §4). Контент за гейтом — не нейтральный: карточки несут emigrant/citizenship-нарратив куратора и адресный список организаций по чувствительным гео (`docs/backlog/BACKLOG.md`), поэтому пробелы разбираются как реальные, не как гигиена ради гигиены.

Граница скоупа: только сам гейт (`_auth.py` и его потребители) и заголовки ответа. Ни `_repo.py` (фильтрация/пагинация), ни схема `postings`/`organizations`/`searches`, ни бизнес-логика где-либо ещё не трогаются.

## 1. Сессионный токен вместо пароля-как-cookie

Сейчас `login.py:37` кладёт в `Set-Cookie` буквально введённый пароль; `_auth.is_authenticated` (`_auth.py:23-30`) сверяет cookie напрямую с `SITE_PASSWORD`. Утечка cookie = утечка мастер-пароля, отозвать одну сессию нельзя не сменив пароль всем.

Новая таблица `auth_state` (`_schema.py`, одна строка `id=1`) с колонкой `epoch INTEGER`. Токен — `f"{epoch}.{issued_at}.{hmac_hex}"`, где `hmac_hex = HMAC-SHA256(key=SITE_PASSWORD, msg=f"{epoch}.{issued_at}")`. `_auth.issue_token(engine, now=None)` создаёт токен на текущий epoch; `_auth.is_authenticated(cookie_header, engine, now=None)` разбирает токен, пересчитывает подпись через `hmac.compare_digest`, сверяет `epoch` с текущим значением в БД и `now - issued_at <= _MAX_AGE` (30 дней, как сейчас — но теперь это серверная проверка, а не только браузерный `Max-Age`, которому раньше ничего не мешало быть обойдённым модифицированной cookie). `now` — необязательный параметр (по умолчанию `time.time()`) специально ради герметичных тестов границы `issued_at`/`_MAX_AGE` без реального ожидания.

`is_authenticated` меняет сигнатуру (добавляется `engine`) — обновляются все три вызывающих места: `postings.py:59`, `status.py:22`, `facets.py:20` (уже вызывают `_repo.get_engine()` следующей строкой, порядок просто меняется местами). `_MAX_AGE` (сейчас объявлена только в `login.py:16`, для атрибута cookie) переезжает в `_auth.py` единственным источником истины — `is_authenticated` использует то же значение для серверной проверки `issued_at`, `login.py` импортирует его для `Set-Cookie`; две независимо объявленные константы одного смысла — ровно класс бага, уже словленного на этом проекте живьём (`MAX_SIZE`/`FACET_SIZE`, `web-postgres-migration/spec.md`).

`auth_state` определяется одной миграцией сразу с полным набором колонок, включая `failed_attempts`/`locked_until` из §4 — второй миграции под rate limiting не будет, только код, использующий уже существующие с коммита 1 колонки.

Деплой коммита 2 инвалидирует любую cookie, выданную старым кодом (буквенное значение пароля не проходит разбор на `epoch.issued_at.hmac`) — ожидаемо, не баг: куратор один раз перелогинивается, как при обычном логауте.

## 2. Logout — глобальная инвалидация

`POST /api/logout` (новый `web/api/logout.py`) — требует аутентификации (иначе анонимный DoS: один POST без cookie мгновенно разлогинил бы куратора), инкрементирует `auth_state.epoch` через `_auth.bump_epoch(engine)` и очищает cookie (`Max-Age=0`). Инвалидация глобальная — у одного куратора нет понятия «выйти только с этого устройства», разлогин применяется ко всем выданным токенам сразу, включая текущий. Кнопка «Logout» в `app.js`/`index.html` рядом с `refresh-btn`.

## 3. Константное сравнение пароля

`check_password` (`_auth.py:19`) и подпись токена переходят на `hmac.compare_digest` вместо `==` — устраняет timing-attack поверхность, изменение на уровне одной строки в каждом месте.

## 4. Rate limiting на `/api/login`

Колонки `failed_attempts INTEGER`, `locked_until TIMESTAMPTZ` в той же строке `auth_state` (определены с коммита 1, см. §1). `_auth.check_login(engine, password, now=None)`: если `locked_until` в будущем — отказ независимо от пароля; иначе сравнение через `compare_digest`; успех — сброс `failed_attempts`; неудача — инкремент, при достижении 10 — `locked_until = now + 15 минут`. Глобальный счётчик, не per-IP: Vercel Functions не дают доверенного клиентского IP без отдельной настройки прокси, а per-IP таблица растёт неограниченно ради масштаба в один аккаунт. `login.py` возвращает `429` вместо `401`, когда залочено.

## 5. Security-заголовки

`web/vercel.json` получает `headers` (формат подтверждён живьём — `vercel.com/docs/project-configuration/vercel-json`, август 2026): `Content-Security-Policy: default-src 'self'; img-src 'self' data:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; connect-src 'self'` (у `index.html` нет ни одного inline `<script>`/`<style>` и ни одного внешнего ресурса — проверено чтением, `'unsafe-inline'` не нужен; `img-src ... data:` явно разрешает существующий inline-SVG favicon, иначе `default-src 'self'` его бы заблокировал), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`. HSTS Vercel уже добавляет по умолчанию (подтверждено веб-поиском) — не трогаем.

## Design rationale / отвергнутые альтернативы

- **Таблица сессий с отзывом по одной штуке** (как RT-ротация в `scopus_search_code`) — отвергнуто: рассчитана на много пользователей и требует чистки устаревших строк; одному куратору достаточно одного глобального `epoch`, состояние — одна строка без роста.
- **Per-IP лимит попыток входа** — отвергнуто: неограниченный рост таблицы, а `x-forwarded-for` без доверенного прокси в любом случае подделываем.
- **Upstash/Redis под rate limiting** — отвергнуто: новый сервис ради одного счётчика; Postgres уже поднят и достаточен на этом объёме записи.
- **PyJWT** (как в `scopus_search_code`) — отвергнуто: полноценный JWT (claims, audience, произвольные алгоритмы) решает задачи многопользовательской системы; здесь нужны ровно три поля и HMAC-подпись — `hmac`+`hashlib` из stdlib этого достаточно без новой зависимости.
- **Vercel Password Protection** — отвергнуто ещё в `vercel-web-gui/spec.md` §4 (недоступна на Hobby), актуальность не изменилась.

## Что разошлось с планом

- **`locked_until` понадобилась явная нормализация timezone-naive/aware** — не было в исходном плане. SQLite (тесты) возвращает `DateTime(timezone=True)` naive-датой при чтении (нет нативной поддержки timezone), Postgres (прод) — aware; сравнение `now < locked_until` без нормализации падало бы `TypeError` именно на Postgres, то есть прошло бы мимо тестов на SQLite и вскрылось бы только в бою. Добавлен `_auth._as_aware_utc()` — приводит naive к UTC перед сравнением, портируемо на обоих диалектах. Живьём подтверждено на Neon staging (см. ниже) — без этого шага прогон падал именно там.
- **Живая HTTP-проверка задеплоенной функции пошла не через preview-деплой, как предполагалось молчаливо, а напрямую в prod.** Preview-URL Vercel закрыт SSO-редиректом (`vercel.com/sso-api`) на этом аккаунте, а `vercel curl` (штатный обход защиты) в текущей CLI 58.5.1 не резолвит переданный домен (`Could not resolve host`) — вероятно, баг beta-команды. Куратор подтвердил прямой прод-деплой явно (`AskUserQuestion`), тест на lockout-порог (10 неудачных попыток) сознательно не гонялся против прода — только против staging (см. ниже), чтобы не заблокировать реальную сессию куратора.
- **Миграция `0003_add_auth_state` и живая проверка auth-логики** прогнаны против Neon staging branch (`STAGING_DATABASE_URL`) перед проверкой в проде — issue/verify токена, `bump_epoch`, lockout после порога и его истечение, сброс попыток при успешном логине — все пять сценариев подтверждены на реальном Postgres, не только на SQLite юнит-тестах.
- Всё остальное — без отклонений от §1–§5.

## Открытые вопросы

Нет — все параметры (30-дневный `_MAX_AGE`, порог 10 попыток/15 минут блокировки, состав CSP) обоснованы в разделах выше и не требуют развилки, которую может решить только куратор; при необходимости меняются позже правкой констант, не архитектуры.

## Вне скоупа

- Разделение ролей Postgres (`neondb_owner` используется и рантаймом, и миграциями) — сознательно исключено куратором из этого аудита как compromise на масштабе одного куратора/одной БД, не дефект.
- OAuth/сторонние провайдеры входа — не нужны одному куратору.
- Мониторинг/алерты на неудачные попытки входа (Sentry и т.п.) — отдельная задача, не блокирует укрепление самого гейта.
- Per-device/per-session отзыв (в отличие от глобального `epoch`) — не имеет смысла при одном пользователе.
